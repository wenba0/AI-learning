## vLLM v1 "Async Scheduling" 架构详解

### 一、整体架构概览

vLLM v1 采用了**多进程 + 异步 IO**的解耦架构，将系统拆分为两个独立进程：

```
┌─────────────────────────────────────┐     ┌─────────────────────────────────────┐
│   前端进程 (AsyncLLM / LLMEngine)    │     │    后端进程 (EngineCoreProc)          │
│                                     │     │                                     │
│  ┌─────────────┐  ┌──────────────┐  │ ZMQ │  ┌──────────────┐  ┌────────────┐  │
│  │InputProcessor│  │OutputProcessor│ ◄─────►  │ EngineCore   │  │ Scheduler  │  │
│  └─────────────┘  └──────────────┘  │     │  └──────────────┘  └────────────┘  │
│                                     │     │                                     │
│  ┌──────────────┐  ┌─────────────┐  │     │  ┌──────────────────────────────┐   │
│  │AsyncMPClient │  │output_handler│  │     │  │   run_busy_loop()            │   │
│  └──────────────┘  └─────────────┘  │     │  │   GPU Model Execution        │   │
└─────────────────────────────────────┘     └──────────────────────────────────────┘
```

### 二、后端进程：`EngineCoreProc` 的忙循环

后端进程的入口是 `EngineCoreProc.run_engine_core()` 静态方法，它在一个**独立子进程**中启动，最终调用 `run_busy_loop()`：

```1041:1051:vllm/v1/engine/core.py
    def run_busy_loop(self):
        """Core busy loop of the EngineCore."""

        # Loop until process is sent a SIGINT or SIGTERM
        while True:
            # 1) Poll the input queue until there is work to do.
            self._process_input_queue()
            # 2) Step the engine core and return the outputs.
            self._process_engine_step()
            # 3) Run any per-step hooks.
            self._process_per_step_hooks()
```

这是一个**纯同步**的 `while True` 循环，但它并不是简单的忙等。关键在于 `_process_input_queue()` 的设计：

```1053:1079:vllm/v1/engine/core.py
    def _process_input_queue(self):
        """Exits when an engine step needs to be performed."""

        waited = False
        while (
            not self.engines_running
            and not self.scheduler.has_requests()
            and not self.batch_queue
            and not self.per_step_hooks
        ):
            if self.input_queue.empty():
                # Drain aborts queue; all aborts are also processed via input_queue.
                with self.aborts_queue.mutex:
                    self.aborts_queue.queue.clear()
                if logger.isEnabledFor(DEBUG):
                    logger.debug("EngineCore waiting for work.")
                    waited = True
            req = self.input_queue.get()
            self._handle_client_request(*req)

        if waited:
            logger.debug("EngineCore loop active.")

        # Handle any more client requests.
        while not self.input_queue.empty():
            req = self.input_queue.get_nowait()
            self._handle_client_request(*req)
```

**关键点**：当没有待处理请求时，`self.input_queue.get()` 会**阻塞等待**（不是忙等），直到有新请求到来。有请求后才开始调度执行。

#### `_process_engine_step()`：单步执行

```1081:1099:vllm/v1/engine/core.py
    def _process_engine_step(self) -> bool:
        """Called only when there are unfinished local requests."""

        # Step the engine core.
        outputs, model_executed = self.step_fn()
        # Put EngineCoreOutputs into the output queue.
        for output in outputs.items() if outputs else ():
            self.output_queue.put_nowait(output)
        # Post-step hook.
        self.post_step(model_executed)

        # If no model execution happened but there are waiting requests
        # (e.g., WAITING_FOR_REMOTE_KVS), yield the GIL briefly to allow
        # background threads (like NIXL handshake) to make progress.
        # Without this, the tight polling loop can starve background threads.
        if not model_executed and self.scheduler.has_unfinished_requests():
            time.sleep(0.001)

        return model_executed
```

这里的 `self.step_fn()` 指向核心的 `EngineCore.step()` 方法：

```375:404:vllm/v1/engine/core.py
    def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
        """Schedule, execute, and make output."""

        if not self.scheduler.has_requests():
            return {}, False
        scheduler_output = self.scheduler.schedule()
        future = self.model_executor.execute_model(scheduler_output, non_block=True)
        grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
        with (
            self.log_error_detail(scheduler_output),
            self.log_iteration_details(scheduler_output),
        ):
            model_output = future.result()
            if model_output is None:
                model_output = self.model_executor.sample_tokens(grammar_output)

        self._process_aborts_queue()
        engine_core_outputs = self.scheduler.update_from_output(
            scheduler_output, model_output
        )

        return engine_core_outputs, scheduler_output.total_num_scheduled_tokens > 0
```

注意 `execute_model(scheduler_output, non_block=True)` —— 模型执行是**非阻塞**的，返回一个 `Future`。在等待 GPU 计算时，`get_grammar_bitmask()` 等 CPU 侧工作可以并行进行。

#### 后端的 IO 线程

`EngineCoreProc` 在初始化时启动了两个**守护线程**来处理 ZMQ 通信：

```771:798:vllm/v1/engine/core.py

            # overlap ZMQ socket IO with GPU since they release the GIL,

                args=( ... ),
                daemon=True,
```

这些线程将 **ZMQ Socket IO** 与 **GPU 计算**解耦：
- `input_thread`：从 ZMQ socket 读取请求 → 反序列化 → 放入 `input_queue`
- `output_thread`：从 `output_queue` 取出结果 → 序列化 → 通过 ZMQ socket 发送

由于这些线程在 IO 时会释放 GIL，因此可以与主循环的 GPU 计算**真正并行**。

#### 2. `output_handler` 异步循环

`AsyncLLM` 的核心驱动力是 `output_handler` 这个 asyncio Task：

```660:711:vllm/v1/engine/async_llm.py
        async def output_handler():
            try:
                while True:
                    # 1) Pull EngineCoreOutputs from the EngineCore.
                    outputs = await engine_core.get_output_async()
                    num_outputs = len(outputs.outputs)
```

**关键设计**：
- `await engine_core.get_output_async()` 从 `asyncio.Queue` 中等待输出，**不阻塞事件循环**
- 输出被分块（chunk）处理，每块之间用 `await asyncio.sleep(0)` 让出控制权，防止长时间占据事件循环
- 处理后的结果通过 `RequestOutputCollector.put()` 推入每个请求的队列

### 四、v1 vs v0 的核心区别

#### v0 模式（`InprocClient` / `LLMEngine`）：**同步、进程内、用户驱动**

#### 核心区别总结

| 维度 | v0 (`InprocClient`/`LLMEngine`) | v1 (`AsyncMPClient`/`AsyncLLM`) |
|---|---|---|
| **进程模型** | 单进程，EngineCore 在主进程内 | 多进程：EngineCore 在独立子进程 |
| **循环驱动** | **用户代码**驱动 `while` 循环调 `step()` | **内部** `run_busy_loop()` 自动驱动 |
| **调度方式** | 同步阻塞：schedule → execute → wait → return | 异步非阻塞：`execute_model(non_block=True)` 返回 Future |
| **IO 模型** | 直接函数调用，无 IPC 开销 | ZMQ Socket + 后台线程 + `asyncio.Queue` |
| **前端并发** | 无并发，`step()` 阻塞直到 GPU 完成 | asyncio 事件循环驱动，`output_handler` Task 并发处理输出 |
| **GPU/CPU 重叠** | 无，CPU 等待 GPU 完成后才能做下一步 | IO 线程释放 GIL，ZMQ 序列化/反序列化与 GPU 计算并行 |
| **结果交付** | `step()` 返回值，同步获取 | `asyncio.Event` 驱动，`RequestOutputCollector` 异步推送 |

#### v1 架构的核心优势

1. **GPU/CPU/IO 三路并行**：后端的 IO 线程（ZMQ 收发、序列化）在 GPU 计算时释放 GIL 并行执行，前端的 asyncio 事件循环在等待后端结果时可以处理新请求
2. **流水线解耦**：`EngineCore.step()` 中 `execute_model(non_block=True)` 允许在等待 GPU 时做 grammar bitmask 等 CPU 工作；`batch_queue` 机制还支持多 batch 流水线并行（Pipeline Parallelism）
3. **事件驱动的前端**：前端不需要轮询，`asyncio.Event` 和 `asyncio.Queue` 使得数千个并发请求可以高效复用同一个事件循环
4. **`async_scheduling` 标志**：控制是否在 worker 进程中直接更新 draft token ids（用于 speculative decoding），避免前端与后端之间额外的同步开销

```406:414:vllm/v1/engine/core.py
    def post_step(self, model_executed: bool) -> None:
        # When using async scheduling we can't get draft token ids in advance,
        # so we update draft token ids in the worker process and don't
        # need to update draft token ids here.
        if not self.async_scheduling and self.use_spec_decode and model_executed:
            draft_token_ids = self.model_executor.take_draft_token_ids()
            if draft_token_ids is not None:
                self.scheduler.update_draft_token_ids(draft_token_ids)
```

简而言之：v0 是一条**串行流水线**（用户调 `step()` → 阻塞等 GPU → 拿结果 → 再调 `step()`），而 v1 是一个**多进程异步流水线**（后端自驱动忙循环 + IO 线程并行 + 前端 asyncio 事件驱动），实现了 GPU 计算、CPU 调度、网络 IO 的最大程度重叠。

## 请求全生命周期：异步调度隐藏了什么

| # | 被隐藏的开销 | 隐藏在哪个阶段背后 | 机制 |
|---|---|---|---|
| **1** | **前端 tokenization + 输入预处理** | 隐藏在后端 GPU 执行之后 | 多进程隔离：前端进程 vs 后端进程完全并行 |
| **2** | **后端反序列化 + Request 构建 + block hash + grammar 编译** | 隐藏在 GPU forward 之后 | input_thread 在 GPU 计算时释放 GIL 并行处理 |

| **5** | **前端 detokenization + stats 计算** | 隐藏在后端下一轮 GPU 执行之后 | 多进程隔离 + asyncio 分块处理避免事件循环饥饿 |

用一张时间线图来直观表示**两轮迭代的重叠**：

```

                            |                          |

                            |--grammar_bitmask_N--|     (CPU与GPU并行)
```

这就是 v1 相比 v0 的根本差异：v0 是单进程单线程的 **`step() → 阻塞等GPU → 序列化 → 发送 → 再step()`** 串行链条；v1 通过**多进程 + IO 线程 + Future + asyncio** 把这条链条拆成了可以重叠的独立流水段，GPU 几乎永远不会因为 CPU 侧的开销而空闲。

### 二、同步调度 vs 异步调度的时间线对比

#### 同步模式（一步一步串行）

```
Step N:
  CPU: [prepare_inputs] [build_attn_meta] ─── 等GPU ──── [D2H copy(阻塞)] [update_scheduler]
  GPU:                                     [===forward===] [===sample===]
                                                                          ↑ synchronize!
Step N+1:
  CPU:                                                                    [prepare_inputs] ...
```

CPU 在 GPU 执行完后必须**同步等待** D2H 拷贝完成，然后才能更新 scheduler 并开始下一步的 prepare_inputs。

#### 异步模式（流水线重叠）

```
Step N:
  CPU: [prepare_inputs_N] [build_attn_N] ──────────────────── [update_scheduler_N]
  GPU (compute stream):                  [====forward_N====] [==sample_N==]
  GPU (copy stream):                                                       [D2H async copy_N]
                                         ↑ event.sync()                    ↑ event.record()
Step N+1:
  CPU:                                    [prepare_inputs_N+1] [build_attn_N+1]
  GPU (compute stream):                                                        [====forward_N+1====]
  GPU (copy stream):   ─── D2H copy_N 继续 ───→ done
```

**prepare_inputs(N+1) 与 D2H copy(N) 在时间上完全重叠！**

### 三、逐代码块分析隐藏的开销

#### 3.1 `synchronize_input_prep()` —— 跨步骤的 pinned memory 保护

```3012:3025:vllm/v1/worker/gpu_model_runner.py
    @contextmanager
    def synchronize_input_prep(self):
        if self.prepare_inputs_event is None:
            yield
            return

        # Ensure prior step has finished with reused CPU tensors.
        # This is required in the async scheduling case because
        # the CPU->GPU transfer happens async.
        self.prepare_inputs_event.synchronize()
        try:
            yield
        finally:
            self.prepare_inputs_event.record()
```

**问题**：`_prepare_inputs()` 写入 pinned CPU tensor（如 `self.input_ids.cpu`、`self.positions.cpu`），然后通过 `non_blocking=True` 启动 CPU→GPU 异步拷贝。如果下一步的 `_prepare_inputs()` 在拷贝完成前覆盖了这些 CPU tensor，数据就会损坏。

**解决**：
- 进入 `synchronize_input_prep()` 时：`event.synchronize()` 等待上一步的**所有 non_blocking 拷贝完成**
- 退出时：`event.record()` 在当前 compute stream 上记录新 event

这意味着**只有** CPU→GPU 拷贝未完成时才需要等待，大多数情况下 GPU forward 时间远大于拷贝时间，所以这个同步几乎是零成本的。

**被隐藏的开销总结**：

| 被隐藏的 CPU/同步开销 | 隐藏在什么背后 | 机制 |
|---|---|---|
| **`_update_states` (Python dict 操作)** | 上一步的 async D2H 拷贝 | D2H 在 copy stream 上执行，CPU 直接开始新一步 |
| **`_prepare_inputs` (numpy 运算: positions, indices, slot_mapping)** | 上一步的 async D2H 拷贝 + 当步的 async H2D 拷贝 | block_table.commit 先启动 DMA，CPU 继续 numpy 运算 |
| **`query_start_loc/seq_lens/positions` 的 H2D 拷贝** | GPU forward (compute stream) | `non_blocking=True` + 流内有序保证 |
| **`_build_attention_metadata` (MLA metadata 构建)** | 上一步的 async D2H 拷贝 | 只创建 GPU tensor 引用，不需等待 H2D 完成 |
| **Sampled token ids 的 D2H 拷贝** | 下一步的 prepare_inputs + build_attn | copy stream 异步执行 |
| **Scheduler.update_from_output 的 `event.synchronize()`** | 上面所有 prepare 时间 | D2H 早已完成，同步几乎零成本 |
| **Draft token ids 的 D2H 拷贝** | 异步调度下大部分**完全消除** | GPU 上直接传递给 drafter，跳过 D2H+H2D 往返 |
| **PP 间的 sampled token 同步** | 下一步的 forward 开头 | broadcast 异步执行，接收延迟到需要时 |

**核心思想**：通过 `non_blocking=True` 消除 CPU↔GPU 之间的显式同步点，用 **CUDA Event** 做最小粒度的跨 stream 同步，用 **pinned memory + 双 CUDA stream** 实现 "compute 和 copy 并行" + "CPU numpy 和 DMA 并行"，让 GPU 在 DeepSeek V3 这种 60 层 MLA + MoE 的巨型 forward 执行时，CPU 侧的所有前处理和上一步的后处理都被完全隐藏。

## MTP/投机解码 + 异步调度：如何在不知道上一步结果时开始下一步

### 核心矛盾

在投机解码中，Step N 生成了 `[target_token, draft_1, draft_2]`，但其中部分 draft 可能被拒绝。正常情况下，Scheduler **必须**等 Step N 的 sampled tokens 到达 CPU，解析出接受了多少（reject 了多少），才能正确设定 Step N+1 的 `num_computed_tokens` 和 input_ids。

异步调度打破了这个限制 —— 它让 **Scheduler 先"乐观假设"全部接受，在 Worker 层面延迟修正**。

---

### 一、Scheduler 层面：AsyncScheduler 的"乐观占位"策略

`AsyncScheduler` 继承自 `Scheduler`，关键区别在 `_update_after_schedule()`：

```18:35:vllm/v1/core/sched/async_scheduler.py
    def _update_after_schedule(self, scheduler_output: SchedulerOutput) -> None:
        super()._update_after_schedule(scheduler_output)
        spec_decode_tokens = scheduler_output.scheduled_spec_decode_tokens
        for req_id in scheduler_output.num_scheduled_tokens:
            request = self.requests[req_id]
            if request.is_prefill_chunk:
                continue

            scheduler_output.pending_structured_output_tokens |= (
                request.use_structured_output and request.num_output_placeholders > 0
            )
            # The request will generate a new token plus num_spec_tokens
            # in this scheduling step.
            cur_num_spec_tokens = len(spec_decode_tokens.get(req_id, ()))
            request.num_output_placeholders += 1 + cur_num_spec_tokens
            # Add placeholders for the new draft/spec tokens.
            # We will update the actual spec token ids in the worker process.
            request.spec_token_ids = self._spec_token_placeholders
```

**关键**：
- `num_output_placeholders += 1 + cur_num_spec_tokens` —— **乐观假设**这一步会产出 1 个 target token + N 个 draft token，全部记为"占位符"
- `spec_token_ids = self._spec_token_placeholders`（即 `[-1, -1, ..., -1]`）—— **用占位符 -1 填充**，因为 scheduler 此时根本不知道真正的 draft token ids 是什么
- Scheduler 不等待上一步的结果就直接安排下一步调度

当上一步的**真实结果**最终到达 Scheduler 时（通过 `update_from_output()`），再做修正：


**修正逻辑**：如果调度了 3 个 draft tokens，但只接受了 1 个（rejected 2 个），则 `num_computed_tokens -= 2`，`num_output_placeholders -= 2`。这些修正发生在 **Step N 的 forward 已经完成之后**，对 Step N 没有影响，只影响后续步骤。

**本质上，异步调度下的 MTP 实现了"推测性调度"（Speculative Scheduling）**：Scheduler 不等结果就按最优情况排期，Worker 在 GPU 上自成闭环地完成 target→sample→draft 全链路（零 D2H），只把一个极小的 `valid_sampled_token_count` 向量异步拷回 CPU 做延迟修正。这样 Scheduler 的调度延迟、CPU 侧的 bookkeeping、以及跨步骤的 token 传递开销都被 GPU compute 完全隐藏了。

### 关键认识：异步调度下，schedule(N+1) 和 execute(N) 不是并行的

先纠正一个常见误解。在 `EngineCore.step()` 中：


**这是一个严格串行的循环**：schedule(N) → execute(N) → update(N) → schedule(N+1) → execute(N+1) → ...

所以 `schedule(N+1)` **一定在 `update_from_output(N)` 之后**执行。Scheduler 在安排下一步时**已经知道**哪些请求停止了。

"异步"体现在**Worker 内部**：Step N 的 GPU forward 和 Step N-1 的 D2H 输出拷贝并行，以及 input 准备的 CPU/GPU 重叠。

### `step_with_batch_queue()` 的真正流水线逻辑

这个函数的核心思想是：**维护一个深度为 2 的 batch 队列**，schedule(N+1) 在 execute(N) 完成之前就跑。

```416:531:vllm/v1/engine/core.py
    def step_with_batch_queue(self):
        batch_queue = self.batch_queue

        if self.scheduler.has_requests():
            # ① 调度一个新batch
            scheduler_output = self.scheduler.schedule()
            # ② 提交 GPU 执行（non_block=True → 不等GPU完成）
            exec_future = self.model_executor.execute_model(
                scheduler_output, non_block=True
            )
            # ③ 提交采样（也是 non_block=True）
            grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
            future = self.model_executor.sample_tokens(
                grammar_output, non_block=True
            )
            # ④ 推入 batch_queue
            batch_queue.appendleft((future, scheduler_output, exec_future))

            if (model_executed
                and len(batch_queue) < self.batch_queue_size   # 队列没满
                and not batch_queue[-1][0].done()):            # 最老的还没完成
                # ⑤ 不阻塞！立即返回 None
                return None, True

        # ⑥ 队列满了或没更多请求 → 阻塞等待最老的batch完成
        future, scheduler_output, exec_model_fut = batch_queue.pop()
        model_output = future.result()        # 这里才阻塞

        # ⑦ 用完成的结果更新 scheduler
        engine_core_outputs = self.scheduler.update_from_output(
            scheduler_output, model_output
        )
        return engine_core_outputs, model_executed
```

**关键在第 ⑤ 步**：当 batch_queue 还没满时（< 2），`step_with_batch_queue()` **不阻塞，直接返回 `None`**。控制权回到 `run_busy_loop()`，立刻又调用 `_process_engine_step()` → `step_with_batch_queue()` → 又跑了一次 `schedule()` + 提交 execute。

| 部分 | 不开 async scheduling (`step()`) | 开 async scheduling (`step_with_batch_queue()`) |
|---|---|---|
| **step 函数** | `step()`：串行 | `step_with_batch_queue()`：流水线 |

| **schedule(N+1) 何时跑** | execute(N) **完成后** | execute(N) **进行中** |
| **GPU→CPU 输出拷贝** | 同步等待 | `AsyncModelRunnerOutput` + 独立 CUDA stream/线程 |
| **CPU→GPU 输入拷贝** | 阻塞式 | `non_blocking=True` + `prepare_inputs_event` 跨步复用 |
| **sampled token 传递** | D2H → CPU list → H2D | GPU 上直接通过 `prev_sampled_token_ids` 传递 |
| **Scheduler 的 draft token ids** | `post_step()` 中从 Worker 取回 | Worker 内部直接处理，Scheduler 用占位符 |

**核心答案**：你之前看到的 `step()` 确实是串行的，那是 **非异步调度** 的路径。开启 `async_scheduling` 后，代码走的是 `step_with_batch_queue()`，它通过一个**深度为 2 的 batch queue** 实现了 "schedule(N+1) 与 execute(N) 的重叠"。在 MultiprocExecutor 下，这个重叠是**真正的跨进程并行**；在 UniProcExecutor 下，GPU 计算是串行的，但 D2H 输出拷贝被异步化到了后台线程，与下一步的 schedule + prepare_inputs 并行。

### 单请求场景下，异步调度到底省了什么

画出**不开**和**开启**异步调度的对比时间线：

#### 不开异步调度（`step()`，串行）

```

Worker GPU:             [prep(N)] [fwd(N)] [sample+draft(N)]           [prep(N+1)] [fwd(N+1)] [sample+draft(N+1)]

                                                  ↑                       ↑
                                        D2H 阻塞等待              sampled token CPU→GPU
                                        sampled_token.tolist()    又要从CPU拷回GPU
                                                  ↑                       ↑
                                               浪费时间                 浪费时间
```

**串行模式的浪费**：
1. D2H 同步等待：`sampled_token_ids` 从 GPU 拷到 CPU（阻塞）
2. Scheduler 的 `update_from_output(N)` 在 CPU 上跑（GPU 空闲）
3. `schedule(N+1)` 在 CPU 上跑（GPU 空闲）
4. `_prepare_inputs(N+1)` 要把 sampled token 从 CPU 拷回 GPU（H2D）

#### 开启异步调度（`step_with_batch_queue()`）

```
EngineCore:  [sched(N)] [submit(N)] [sched(N+1)] [submit(N+1)] ── [等future_N] [update(N)] [sched(N+2)] ...
                              │            │                            ↑
                              ▼            ▼                            │
Worker:               [prep(N)] [fwd(N)] [sample+draft(N)] [prep(N+1)] [fwd(N+1)] ...
                                                      │         ↑
                                                      │    GPU→GPU scatter
                                                      │    (prev_sampled_token_ids)
                                                      │    无D2H！无H2D！
                                                      ▼
                                              D2H在copy stream上异步执行
                                              与prep(N+1)并行
```

**省掉的时间**：

| # | 省掉了什么 | 大约耗时 | 怎么省的 |
|---|---|---|---|
| **1** | `schedule(N+1)` 的 CPU 时间 | ~0.1-0.5ms | 在 Worker 跑 step N 时，EngineCore **并行**完成 schedule(N+1) |
| **2** | `grammar_bitmask(N+1)` 的 CPU 时间 | ~0.1ms | 同上，并行完成 |
| **3** | sampled tokens 的 D2H 同步等待 | ~0.05-0.2ms | `AsyncModelRunnerOutput` + copy stream 异步拷贝，不阻塞 |
| **4** | sampled tokens 的 H2D 传回（input_ids） | **完全消除** | `prev_sampled_token_ids` 留在 GPU 上，GPU→GPU scatter |
| **5** | draft tokens 的 D2H + H2D 往返 | **完全消除** | `_draft_token_ids` 留在 GPU 上，直接 scatter 进 input_ids |
| **6** | `_prepare_inputs(N+1)` 中部分 CPU numpy 运算 | ~0.05-0.1ms | 与上一步的 D2H 异步拷贝并行 |
| **7** | Scheduler 处理 draft token ids 的 CPU 往返 | **完全消除** | `post_step()` 跳过 `take_draft_token_ids`，Worker 内部处理 |

对于单请求，假设 GPU forward 耗时 30ms，**每个 step 大约省 0.5-1.5ms**。看起来不多，但这意味着每秒多出 1-2 个 token 的生成速度（在 decode 阶段尤其显著）。

### batch_queue 里 N 和 N+1 是怎么"叠加"的

用一张图展示 batch_queue 在稳态下的状态变化：

```
时间 →

run_busy_loop 第1轮:
  step_with_batch_queue():
    schedule(N), submit(N)
    queue: [N]  (size 1 < 2, return None)

run_busy_loop 第2轮:
  step_with_batch_queue():
    schedule(N+1), submit(N+1)        ← schedule(N+1) 与 Worker 执行 N 并行！
    queue: [N+1, N]  (size 2 = max)
    pop(N), 等 N 完成, update(N)
    queue: [N+1]
    return outputs_N

run_busy_loop 第3轮:
  step_with_batch_queue():
    schedule(N+2), submit(N+2)        ← schedule(N+2) 与 Worker 执行 N+1 并行！
    queue: [N+2, N+1]  (size 2 = max)
    pop(N+1), 等 N+1 完成, update(N+1)
    queue: [N+2]
    return outputs_N+1

...循环...
```

**batch_queue 里的 N 和 N+1 都是同一个请求的不同 step**。它们在 GPU 上是串行的（Worker 按顺序处理），但 EngineCore 的 schedule 和 Worker 的 execute 在**不同进程/不同时间片**上重叠执行。

所以更精确地说：**async scheduling 减少的不是 GPU 计算时间，而是每两个 step 之间的 "CPU 间隙"** —— 那段 GPU 空闲着等 CPU 做调度、做 D2H/H2D 拷贝、做 token 传递的时间。对于 DeepSeek V3 这种 decode 阶段 GPU forward 只需要十几到几十毫秒的场景，这 0.5-1.5ms 的 CPU 间隙可以占到 step 总时间的 3%-10%，消除它就是实实在在的 TPOT (Time Per Output Token) 提升。

### 1. 非 Spec Decode 场景：`_to_list()` 的同步

```6188:6201:vllm/v1/worker/gpu_model_runner.py

        # https://github.com/vllm-project/vllm/issues/22754.
        # `tolist` would trigger a cuda wise stream sync, which
        # would block other copy ops from other cuda streams.

        # this is in the critical path of every single model
```

## 二、异步调度为什么必须用 Triton

异步调度的核心设计目标是：**`sample_tokens()` 尽快返回**，让 EngineCore 的 CPU 可以立即开始调度下一个 batch。这意味着**不能在 sample_tokens 的关键路径上有任何 D2H 同步**。

### 不带 Spec Decode 的简单场景

不需要 Triton。异步路径直接把 `sampled_token_ids` 留在 GPU 上：

```2945:2961:vllm/v1/worker/gpu_model_runner.py

            invalid_req_indices = discard_sampled_tokens_req_indices.tolist()
            invalid_req_indices_set = set(invalid_req_indices)

            # These will be copied into input_ids in the next step
            # when preparing inputs.
            # With spec decoding, this is done in propose_draft_token_ids().
```

下一步 `_prepare_input_ids` 时用 GPU-to-GPU scatter 直接从 `prev_sampled_token_ids` 取数据。这里不需要 Triton 因为操作极其简单——就是存个引用。

### 带 Spec Decode（MTP/EAGLE）的复杂场景——**这里 Triton 是必须的**

Spec decode 完成后，rejection sampling 的输出是一个 `[batch_size, max_spec_len+1]` 的 GPU tensor，被拒绝的位置标记为 -1。在非异步路径中，CPU 通过 `.cpu().numpy()` + Python 循环来处理这个结果。但异步路径**不能有这个同步**。

CPU 需要知道的关键信息是：
1. **每个请求接受了多少 token**（`valid_sampled_tokens_count`）——用于更新 `num_computed_tokens`
2. **最后一个被接受的 token 是什么**（`next_token_ids`）——用于 drafter 的下一轮输入

**这些计算在非异步路径是 CPU 做的**（`.cpu()` 后 Python 循环），但**异步路径必须在 GPU 上做**来避免同步。这就是 Triton 的用武之地：

## 四、从 CUDA 执行模型的角度理解"避免同步"

### 关键原理：Triton kernel launch 是异步的

当 CPU 调用 `triton_kernel[grid](...)` 时：

```
CPU 时间线: ─── launch kernel (几微秒) ── 返回 ── 继续做其他事 ──→
GPU 时间线: ─── 等待排队 ─── 执行 kernel ─── 写入结果 ──→
```

kernel launch 只是把一个任务放入 GPU 的命令队列，**CPU 不等待 GPU 执行完毕就立刻返回**。这和以下操作形成鲜明对比：

```
# .cpu() 触发隐式同步
tensor.cpu()
# 等价于：
cudaStreamSynchronize(default_stream)  # ← CPU 阻塞，直到 GPU 上所有操作完成
cudaMemcpy(D2H)

CPU 时间线: ─── 调用 .cpu() ── 阻塞等待... ── 阻塞等待... ── 数据到达 ── 继续 ──→
GPU 时间线: ─── 执行中... ──── 执行中... ──── 完成 ─── DMA 拷贝 ─────────→
```

### 异步调度 + MTP 的完整时间线

```
GPU stream 0:  model_forward → sample → rejection_kernel → eagle_prepare_kernel → drafter_forward → ...
GPU stream 1:                                              async_copy(valid_count) → ...
GPU stream 2:                                                         async_copy(sampled_tokens for output) → ...
CPU:           launch(μs) → launch(μs) → launch(μs) → _bookkeeping(留GPU) → return → 调度 N+1 → ...
                                                                                          ↑
                                                                      不等 GPU！立即开始下一轮
```

对比非异步路径：

```
GPU stream 0:  model_forward → sample → rejection_kernel → idle...
CPU:           launch(μs) → .cpu()(阻塞 ~0.5-1ms) → Python 循环 → return → 调度 N+1 → ...
                                      ↑ 同步点，CPU 被卡住
```

### 那 `valid_sampled_tokens_count` 最终还是要到 CPU 的？

是的，但它是**异步拷贝**的：

```3908:3925:vllm/v1/worker/gpu_model_runner.py
    def _copy_valid_sampled_token_count(
        self, next_token_ids: torch.Tensor, valid_sampled_tokens_count: torch.Tensor
    ) -> None:
        # ...
        # 在单独的 CUDA stream 上异步拷贝
        with torch.cuda.stream(self.valid_sampled_token_count_copy_stream):
            self.valid_sampled_token_count_copy_stream.wait_stream(default_stream)
            counts_cpu = self.valid_sampled_token_count_cpu
            counts_cpu[: counts.shape[0]].copy_(counts, non_blocking=True)
            self.valid_sampled_token_count_event.record()

        self.input_batch.prev_sampled_token_ids = next_token_ids.unsqueeze(1)
```

这个 D2H 拷贝在**独立的 stream 2** 上发起，CPU 不等待它完成就继续。只有在下一步真正需要这个数据时才同步：

```3927:3937:vllm/v1/worker/gpu_model_runner.py
    def _get_valid_sampled_token_count(self) -> list[int]:
        prev_sampled_token_ids = self.input_batch.prev_sampled_token_ids
        sampled_count_event = self.valid_sampled_token_count_event
        if sampled_count_event is None or prev_sampled_token_ids is None:
            return []
        counts_cpu = self.valid_sampled_token_count_cpu
        sampled_count_event.synchronize()  # ← 到这里才等
        return counts_cpu[: prev_sampled_token_ids.shape[0]].tolist()
```

到调用 `_get_valid_sampled_token_count` 时，drafter forward 已经跑完了，这个 D2H 拷贝（只有 `batch_size` 个 int32，几十 bytes）早就完成了，**event sync 几乎不阻塞**。

## 五、总结

| 操作 | 非异步路径 | 异步路径 + Triton |
|------|-----------|-------------------|
| Rejection sampling | Triton kernel (GPU) | 同左 |
| 统计 valid count | `.cpu()` + Python 循环 (CPU 同步) | `eagle_prepare_next_token_padded_kernel` (GPU) |
| 找 next token id | `.cpu()` + Python 循环 (CPU 同步) | 同上 kernel 一并计算 (GPU) |
| 计算被拒绝数 | CPU 计算 | `eagle_prepare_inputs_padded_kernel` (GPU) |
| sampled tokens 传递 | D2H → CPU list → H2D 下一步 | 留 GPU `prev_sampled_token_ids` |
| valid count 到 CPU | 在关键路径上同步 | 独立 stream 异步拷贝，延迟同步 |

**一句话概括**：Triton 让原本需要"GPU→CPU→处理→GPU"的后处理链变成了"GPU→GPU→GPU"的纯 GPU 流水线，唯一需要到 CPU 的少量数据（`valid_sampled_tokens_count`，几十字节）通过独立 CUDA stream 异步拷贝，不阻塞 CPU 的调度关键路径。这就是为什么异步调度+MTP 必须依赖 Triton 做后处理——**不是因为 Triton 算得快，而是因为 Triton 算完的结果可以留在 GPU 上，避免了 `.cpu()` 带来的全局流同步**。

## 用 PyTorch 替代 Triton 完全可行

以 `eagle_prepare_next_token_padded_kernel` 为例，等价的 PyTorch 写法大概是：

```python
# sampled_token_ids: [batch_size, num_spec_tokens + 1], GPU tensor
# 被拒绝的位置值为 -1

valid_mask = (sampled_token_ids != -1) & (sampled_token_ids < vocab_size)
# valid_count: [batch_size]  —— 还在 GPU 上
valid_count = valid_mask.sum(dim=-1)

# 找最后一个合法 token 的 index
indices = torch.arange(sampled_token_ids.shape[-1], device=sampled_token_ids.device)
masked_indices = torch.where(valid_mask, indices, -1)
last_valid_index = masked_indices.argmax(dim=-1)  # [batch_size]

# 取出对应的 token id
next_token_ids = sampled_token_ids.gather(1, last_valid_index.unsqueeze(1)).squeeze(1)

# 处理 discard 的请求
next_token_ids = torch.where(discard_mask, backup_tokens, next_token_ids)
valid_count = torch.where(discard_mask, 0, valid_count)
```

**这段代码的结果同样全部在 GPU 上**，不需要 `.cpu()`，不会触发同步。所以从"能否避免同步"这个角度讲，**PyTorch 和 Triton 的效果完全相同**。

## 那为什么选 Triton 而不是 PyTorch？

原因不是"能不能避免同步"，而是**kernel launch overhead 和内存访问效率**：

### 1. Kernel Launch 次数

上面那段 PyTorch 代码，每一行 torch 操作都是一次独立的 CUDA kernel launch：

```
torch.ne()          → kernel launch #1  (~3-5μs)
torch.lt()          → kernel launch #2
torch.bitwise_and() → kernel launch #3
torch.sum()         → kernel launch #4
torch.arange()      → kernel launch #5
torch.where()       → kernel launch #6
torch.argmax()      → kernel launch #7
torch.gather()      → kernel launch #8
torch.where() × 2   → kernel launch #9, #10
```

大约 **10 次 kernel launch**，每次 ~3-5μs 的 CPU 端开销，累计 **30-50μs**。

Triton 版本是 **1 次 kernel launch**，~3-5μs。

### 2. HBM 读写次数

PyTorch 每个 op 都要：**读输入 → 计算 → 写中间结果到 HBM → 下一个 op 再读**。10 个 op 意味着 `sampled_token_ids` 这个 tensor 可能被反复从 HBM 读取多次。

Triton 版本：**读一次 `sampled_token_ids` 到寄存器/SRAM，在芯片内算完所有逻辑，写一次结果**。

### 3. 量化评估

对于 MTP 场景的这些后处理操作：
- 数据量很小（batch_size × 几个 int32）
- 计算量也很小（比较、求和、argmax）
- **瓶颈完全是 kernel launch 开销，不是计算或带宽**

所以 Triton 对比 PyTorch 的优势主要体现在：
- 10 次 launch → 1 次 launch，省 ~30-40μs
- 这在每个 decode step 都要执行，如果 TPOT 目标是 10-20ms，30-40μs 也是 0.2-0.4% 的开销

## 总结

| | 能避免 CPU-GPU 同步？ | Kernel Launch | HBM 访问 |
|---|---|---|---|
| **Triton** | 能 | 1 次 | 1 读 1 写 |
| **PyTorch（不调 .cpu()）** | **同样能** | ~10 次 | 多次重复读写 |
| **PyTorch（调 .cpu()）** | 不能 | N/A | N/A（同步阻塞） |

所以更准确的说法是：**异步调度要求后处理结果留在 GPU 上，这点 PyTorch 和 Triton 都能做到。选 Triton 是为了把这段关键路径上的 launch overhead 从 ~40μs 压到 ~5μs，是性能优化而非功能必须。**
